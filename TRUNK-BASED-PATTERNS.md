# Trunk-Based Patterns

How this repository branches. Binding for humans and agents alike.
Machine-readable form: `trunk-based.json` (repo root). Enforced by a PreToolUse
guard, `scripts/githooks/pre-push` (version-controlled; both installers point
`core.hooksPath` there), and remote branch protection.

> Generated by the `trunk-based-development` skill. Re-run it to change any of
> this rather than editing both files by hand and letting them drift.

## The lines

| | Branch | Rules |
|---|---|---|
| **Trunk** | `main` | The single integration line. Always green, always releasable. Never force-pushed, never deleted. |
| **Deployment** | none | Release strategy: `trunk`. Any green `main` commit is deployable; there is no deployment branch. |
| **Leaves** | `leaf/<type>/<slug>` | Disposable. Max 24 hours. Max 3 open at once. Deleted on merge. |

`<type>` ∈ `feat` `fix` `refactor` `chore` `docs` `test` `perf`

## Verify

```
uv run --extra dev pytest -q
```

The 72-test unit suite. It must run where **git** runs it — the pre-push hook has
no venv activated, and `python` is not on PATH on every machine that clones this
repo, so the obvious-looking `python -m pytest -q` fails with *command not found*
and rejects every push. `uv` is a single cross-platform binary and this repo already
ships a `uv.lock`, so it resolves the project environment itself instead of pinning
`.venv_sh/bin/python` (which would break the Windows checkout).

`--extra dev` is required, not cosmetic: `pytest` is declared in the `dev` extra, so
a plain `uv sync` / `uv run` resolves the project **without** pytest and the gate
cannot start (`Failed to spawn: pytest`). This form also needs no setup step — uv
creates `.venv` on first use, so verify works on a clone that has never been
installed. Earlier this file specified `--no-sync`, which could not work on a fresh
clone: nothing creates the `.venv` that `uv run` resolves, since `install.sh` builds
`.venv_sh` and `install.ps1` builds `.venv_windows`.

`.venv` is the **verify-only** environment. It is deliberately not the venv the MCP
server runs from (`.venv_sh` / `.venv_windows`), so a push never mutates a live
server's interpreter — which is what `--no-sync` was reaching for.

`scripts/validate.py` is the heavier harness — it synthesizes a >1M-token log, a
k8s manifest set and a repo dump and drives the load/inspect/chunk/exec tools
against the real Docker sandbox. It is **not** part of verify because it needs
Docker up and takes minutes. Run it by hand before anything that touches the
sandbox or context-store path.

Verify runs **before** a leaf merges, not after. A leaf that has not passed it
does not reach `main`. Failing verify is not a reason to merge with a note — fix
it or drop the leaf.

Review gate: **`self-on-green`**.

## The loop

```
 1. SYNC      git switch main && git pull --ff-only
 2. BUDGET    at 3 leaves? land or delete one first
 3. SCOPE     one landable increment inside 24h; else split, or land it dark
 4. LEAF      git switch -c leaf/<type>/<slug>        (from main, never from a leaf)
 5. WORK      small commits, in this repo, in place
 6. FRESHEN   git fetch && git rebase main
 7. VERIFY    uv run --no-sync pytest -q  — it must pass
 8. GATE      releasable? incomplete work is flagged off, not held back
 9. REVIEW    self-on-green: a green verify is the approval
10. LAND      git switch main && git merge --no-ff leaf/... && git push
11. DELETE    git branch -d leaf/... && git push origin --delete leaf/...
12. CONFIRM   main still green? red → fix or revert within minutes
```

**Why `--no-ff` and not `--squash`.** `allow_direct_trunk_commits` is `false`, and
`git merge --squash` leaves the result staged and requires a follow-up
`git commit` **on trunk** — which the guard blocks, by design. `--no-ff` creates
its own merge commit, so landing works without ever weakening trunk protection or
reaching for `--no-verify`. Keep leaves to a couple of commits and trunk history
stays readable.

## Work that does not fit one leaf

Never hold the branch open. Three moves, in preference order:

1. **Split it.** Land the refactor first, the behaviour second.
2. **Land it dark.** There is no flag library here. The nearest mechanism is a key
   in `src/config.py` `_DEFAULTS` plus its `Config` field, overridable from
   `config.yaml`: default the new path off and gate on `cfg.<key>`. Add a real
   flag module only when something actually needs it — and delete the key once the
   path is permanent, or it becomes another dead knob.
3. **Branch by abstraction.** For a replacement spanning many leaves: put an
   abstraction in front of the old implementation, build the new one behind the
   same shape, migrate callers one leaf at a time, delete the old one last.

## Releases — strategy `trunk`

Tag a green `main` commit, deploy it, fix forward. There is no deployment branch
and nothing is ever cherry-picked. "Deploy" for this server means the MCP
registration in `~/.claude.json` pointing at `run_server.sh`, so a release is
whatever `main` says plus a server reconnect.

**A running server holds its own copy.** Python imported `src/` at startup, so
editing files on disk changes nothing until the process restarts. That cuts both
ways: landing on `main` is safe while a session is live, and a fix does not take
effect until the MCP server is reconnected.

## Banned

| Banned | Instead |
|---|---|
| `git worktree add`, agent worktree isolation | Work in this repo, on a leaf |
| Cloning or copying this repo to a scratch dir | Same |
| Long-lived `develop` / `staging` / `integration` | `main` is the integration point |
| Branching off a leaf; stacked leaves | Fork from `main` only |
| A leaf older than 24h | Split it, or land it dark |
| More than 3 leaves open | Land or delete first |
| Force-push to `main` | Fix forward, or revert |
| Stashing work instead of landing it | Land a smaller increment |
| Merging on red verify to unblock | Fix it, or drop the leaf |
| Code freezes, integration phases | Not needed when leaves are hours old |
| Monkey-patching the engine from `src/` | The engine is vendored source at `./rlm` — fix the defect there (see `rlm/UPSTREAM.md`) |

The deployment-branch bans (no back-merge, no direct commits on a release line)
do not apply: strategy `trunk` has no such branch. Changing strategy means
re-running the skill, not hand-editing these two files.

## Targets

| Measure | Target |
|---|---|
| Active branches | ≤ 3 |
| Oldest leaf | < 24 hours |
| Merges to `main` | ≥ 1 per developer per day |
| Code-freeze days | 0 |
| Time to review a leaf | minutes, not hours |

## If you are an AI agent

Read this file before touching code. You are on step 1 until you say otherwise;
name the step you are on as you go. If you skip a step, say which and why. When a
guard blocks you, the block message names the compliant alternative — take it.
Do not work around a guard, and do not reach for `--no-verify`.
